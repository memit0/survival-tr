# Evaluation and optimization

## Start with a meaningful collection

Use your actual Turkish articles, not just selected answer passages. Leave distractors in the search space. Record source/version and retain the exact original Unicode text. First ask: does the answer exist in this corpus? Retrieval cannot invent missing knowledge.

The bundled 12 fictional articles and 26 AI-authored questions only exercise the pipeline. They are small, stylistically related, and not independently annotated. High demo scores are not evidence of general Turkish accuracy. Do not use them to select a production model or calibrate an emergency assistant.

## Question format

One JSON object per line:

```json
{"qid":"q001","query":"Kayıt olmak için ücret ödemem gerekiyor mu?","group":"membership-fee","category":"paraphrase","split":"dev","answerable":true,"relevant":[{"article_id":"library-membership","grade":2,"evidence":[{"start":8,"end":36}]}]}
```

Offsets in that example are illustrative: measure them against YOUR article text. Offsets are Python Unicode character positions, start inclusive/end exclusive, not UTF-8 bytes. In JavaScript, non-BMP characters have different UTF-16 offsets. A helper for known text is `start = text.index(answer_span); end = start + len(answer_span)` in Python.

An unanswerable question has `answerable: false` and no grade-2 labels. Every answerable question must have at least one grade-2 article. Grade 0 = does not answer; 1 = partial; 2 = sufficient. Include all valid alternative articles. Each evidence span is an **alternative sufficient contiguous span**, not one fragment of a multi-part answer. If two sentences are jointly necessary, mark a single span covering both. A passage succeeds only when it contains an entire sufficient span.

## Build labels carefully

Start with 50 questions to debug the process, then collect hundreds in natural Turkish. Include direct questions, paraphrases, misspellings, suffix variants, missing diacritics, numbers, named entities, negation and near-topic unanswerables. Ask people for questions before showing article wording when possible.

Retrieve pooled candidates from BM25, dense and hybrid systems. Judge the union plus manually identified answers. A passage on the same topic is not necessarily an answer. Have a second Turkish reader label a subset independently; resolve disagreements. Unjudged results currently count as irrelevant, so incomplete labels can unfairly punish a genuinely useful result.

Assign paraphrases of the same intent to a shared `group` and keep that group within one split. The validator rejects cross-split family leakage. Use `train` only for any future fine-tuning, `dev` for tuning, and `test` once for final selection. Native test questions should not be generated by copying test answers/headings. Indexing test-relevant articles is normal; leaking held-out query labels into tuning is not.

## What is actually measured?

| Metric | Denominator / rule |
|---|---|
| Article Success@1/@3 | Answerable questions; at least one grade-2 article in first 1/3 distinct articles |
| Recall@3 | Fraction of grade-2 articles found in first three, averaged over answerable questions |
| MRR@10 | Reciprocal rank of first grade-2 article, else 0 |
| nDCG@10 | Article grades 0/1/2, gains `2^grade - 1`, log2 discount, normalized by ideal order |
| Excerpt Success@1 | Answerable questions WITH labeled grade-2 evidence; first displayed article excerpt must contain it |
| Candidate Success@20 | Same evidence-labeled subset; a sufficient span must appear in first 20 ranked passages |
| False acceptance | Unanswerable questions where any result survives the acceptance policy |
| False rejection | Answerable questions where no result survives |

Candidate Success@20 is measured on the returned, threshold-filtered passage ranking. For diagnosing first-stage retrieval use no threshold first. Hybrid considers the union of top `--candidates` lists (default 50 each); dense ranks the full collection exactly. No reranker is implemented.

`success_at_1` does not prove the displayed text is factually correct; it proves it matched the annotated article. Evidence metrics catch the case where the right article is retrieved with the wrong excerpt. When changing chunking, article IDs and evidence offsets remain stable.

## Reproducible experiments

Create one immutable prepared dataset/index/report path per configuration. Commands never overwrite them. Model bundle fingerprints, corpus/query hashes, model backend, precision export identity, token budgets, lexical settings, package versions, hardware platform, rankings and per-query metrics are saved. Pin `download-model --revision COMMIT_SHA` for future builds. Model artifact files themselves are not committed to GitHub.

Example experiment sequence:

1. E5-small FP32, 240-token chunks, same corpus and questions.
2. BM25 on those same chunks, with and without stemming/folding (separate indexes).
3. Hybrid on the winning lexical configuration.
4. 160/240/320-token chunk comparisons; headings/overlap experiments.
5. INT8 ONNX with separately rebuilt passage vectors.
6. Only then consider a larger encoder or reranker.

Use `tr-search compare reports/a reports/b` for paired deltas and Success@1 group-bootstrap intervals. Right-minus-left positive means improvement. Comparisons require the same articles, queries and split; chunking can differ. Bootstrap resamples question families, preserving family dependence. Tiny demo sets produce unstable intervals. Review regressions as well as wins, and inspect category breakdowns. Avoid selecting from hundreds of variants based on a small dev set.

## Acceptance / no-answer tuning

Dense retrieval always has a nearest neighbor; without a threshold it normally returns an article even for an unanswerable query. BM25 only suppresses queries with no positive lexical matches. Neither has calibrated confidence.

`--min-dense-score X` filters dense/hybrid passages by raw cosine score. It is intentionally unset. On dev only, run multiple fresh report directories over candidate thresholds, e.g. `0.70`, `0.75`, `0.80`, `0.85`; those numbers are a sweep example, not recommendations. Plot/tabulate false accepts vs false rejects. Choose using your error costs, then freeze the cutoff and test it on a held-out set. Model, precision or corpus changes require recalibration. No cutoff establishes guaranteed answerability.

## Optimize by failure type

- Answer absent: acquire/repair source content.
- Answer span split: change chunk boundaries/context before changing models.
- Correct candidate in top 20, poor first result: investigate ranking, hybrid weights or a reranker.
- Correct passage never retrieved: improve first-stage retrieval, query variants or retrieval-specific fine-tuning.
- Diacritic/suffix misses: inspect lexical preprocessing and native Turkish examples.
- Correct article, wrong excerpt: fix passage ranking or aggregation.
- High false acceptance: improve labels and acceptance policy; do not treat cosine as a probability.

Fine-tuning is a future extension, not included code: use reviewed query/positive/hard-negative triples; ensure a presumed negative isn't another valid answer. Distillation is another future option: train a small model to imitate a stronger teacher offline. Both need train/dev/test separation and do not guarantee improvement.

## Resource measurements

Warm P50/P95 excludes initial model load and two warm-up questions. Searcher load time excludes model initialization. `index_bytes` excludes the model and Python dependencies. To measure a complete cold CLI run on macOS, use `/usr/bin/time -l tr-search search ...`; inspect maximum resident set size and elapsed time. On Linux use `/usr/bin/time -v`. Measure the model directory and full application separately, and record CPU, thread settings, power mode and repeated runs. Do not compare laptop timings directly with published GPU figures.
